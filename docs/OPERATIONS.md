# 운영·복구 안내 (P0, 로컬/파일럿 기준)

이 문서는 로컬·파일럿 환경 기준입니다. 실제 호스팅은 아직 정하지 않았습니다(명세 15장). 배포·학생 초대·메일·결제는 별도 승인 전까지 하지 않습니다.

## 1. 구성 요소

| 구성 | 역할 | 실행 |
|---|---|---|
| PostgreSQL 16 (Supabase 호환) | 모든 도메인 데이터, RLS, 작업 큐(`app_jobs`), 비용 원장 | `pnpm db:local` (임시 클러스터 `.tmp/pg`, 포트 54329) |
| 웹 (`apps/web`) | 화면 + `/api/v1`, 서버 액션 | 개발 `pnpm dev:web`, 프로덕션 `pnpm --filter @xhs/web build && pnpm --filter @xhs/web start` |
| 워커 (`apps/worker`) | `app_jobs` 폴링·임대(lease) 실행, 매시간 만료 정리 | `pnpm dev:worker` |
| 비공개 파일 저장소 | 업로드 파일(메타데이터 제거 후) | `ASSET_STORAGE_DIR` (기본 `.data/assets`), 배포 시 Supabase 비공개 Storage로 교체 |

필수 환경변수는 `.env.example`을 따릅니다. 비밀값은 `.env.local` 또는 서버 secret에만 둡니다. 채팅·문서·git·로그에는 넣지 않습니다. `NEXT_PUBLIC_`에는 비밀을 넣지 않습니다.

## 2. mock 모드 보장

- `APP_DATA_MODE=mock`이 기본값입니다. API 키가 있어도 live로 바뀌지 않습니다.
- 웹·워커는 시작할 때 **외부 연결 차단 가드**를 설치합니다. 로그 `mock mode: outbound network guard active (web|worker)`가 그 표시입니다. 이후 루프백·DB 외 TCP 연결은 거부되고 `[network-guard] blocked outbound connection to …`가 남습니다.
- 운영 점검: 로그에서 `[network-guard]`를 검색합니다. 한 건이라도 있으면 원인을 조사합니다(`pnpm test:e2e`는 이 경우 실패합니다).
- `next dev`는 자체 버전 확인을 위해 npm 레지스트리 접속을 시도하므로, 가드 로그가 한 줄 남을 수 있습니다. 앱 동작과는 무관하며, 시연·검증은 프로덕션 빌드로 합니다.

## 3. 작업(job) 상태와 복구

- 비용이 드는 작업은 모두 **견적(5분·1회용) → 확인 → `app.reserve_and_enqueue`** 순서를 거칩니다. 이 단계는 한 트랜잭션으로 처리됩니다: 견적 소비, 예산 잠금, 원장 기록, 작업 생성, idempotency 키 저장.
- 워커는 `app.claim_job`으로 작업을 **5분 임대**합니다. 워커가 죽으면 임대가 끝난 뒤 다른 워커가 다시 가져갑니다(`attempts` 증가). 같은 작업이 두 번 동시에 실행되지는 않습니다.
- 외부로 보냈는데 결과를 모르면 `unknown_outcome`으로 둡니다. 자동으로 재시도하지 않습니다(이중 과금 방지). 관리자가 `/admin/jobs`에서 확인하고, 필요하면 `/admin/usage`의 정산(reconcile)으로 원장을 `settled`/`released`로 맞춥니다.
- 대기(`queued`/`waiting_external`) 작업은 학생 화면이나 `/admin/jobs`에서 취소할 수 있습니다. 이미 외부로 보낸 처리와 비용은 취소가 보장되지 않으며, 화면에도 그렇게 표시합니다.
- 긴급 중지: `/admin/providers`의 **외부 작업 모두 중지(kill)** 를 켜면 새 견적과 대기 중인 작업 실행이 모두 막힙니다. 기능별 스위치(AI·음성 문안·외부 조회)와 일일 한도(`/admin/usage`)는 리비전을 확인한 뒤 저장되므로, 동시에 수정하면 충돌로 거부됩니다.

## 4. 데이터 삭제·만료

- 학생 "내 데이터 삭제"(`/app/privacy`): 요청 즉시 접근을 막고 진행 중 제출을 철회합니다. 이어서 `user_deletion` 작업이 비공개 자료·파일·파생 결과를 지웁니다. 비용 원장과 보안 감사 기록은 회계·보안 보존 정책(기본 90일 제안)에 따라 남기고, 상태를 `partially_retained`로 표시하며 이유를 함께 적습니다. 학생 문안은 남기지 않습니다.
- 만료 정리(워커, 매시간 `purgeExpired`): 대상은 만료된 공급자 노트(레퍼런스가 참조하지 않는 것), 만료된 음성 문안, 만료된 idempotency 키(유료 작업 보유분 제외), 오래된 미사용 견적입니다. 정리 작업이 실패해도 조회 쿼리가 `expires_at`을 직접 검사하므로 만료 자료는 노출되지 않습니다.
- 삭제는 `app.allow_purge` 설정이 켜진 서비스 트랜잭션에서만 허용됩니다(실수로 인한 대량 삭제 방지).
- 조직 탈퇴(`/app/privacy`의 "조직에서 나가기"):
  - 처리: 위와 같은 즉시 차단을 한 뒤 멤버십을 `left`로 바꾸고, 같은 삭제 작업을 실행합니다. 다른 조직의 자료에는 영향이 없습니다.
  - 마지막 활성 관리자는 다른 관리자를 지정하기 전에는 나갈 수 없습니다.
  - 탈퇴한 멤버는 관리자 화면에 "탈퇴함"으로 표시되고 재활성화할 수 없습니다. 다시 참여하려면 새 초대 링크가 필요합니다.
- 삭제 작업은 요청자가 이후 중지되거나 탈퇴해도 실행됩니다.

## 5. 백업·복원 (파일럿 권고)

로컬 임시 DB는 백업 대상이 아닙니다. 파일럿 DB는 다음을 권고합니다(아직 자동화하지 않음).

1. 매일 `pg_dump --format=custom`으로 덤프하고, 비공개 파일 저장소도 같은 시점으로 스냅샷합니다. 백업은 암호화해 접근을 제한합니다.
2. 복원 후에는 백업 시점 이후 완료된 `deletion_requests`를 조회해 해당 사용자의 `user_deletion` 작업을 다시 실행합니다(삭제 tombstone 재적용). 이 절차는 **수동**입니다. "백업에서 즉시 소거된다"고 안내하지 않습니다.
3. 복원 리허설 결과(소요 시간, 재적용 건수)를 기록합니다.

## 6. 감사·모니터링

- 감사 기록: `/admin/audit`. 대상은 멤버 역할·중지, 초대, 기수, 스위치·한도, 공급자 허가, 자료실 공개·철회, 신고에 따른 비공개, 삭제 요청입니다.
- 오류·권리 신고: `/review/reports`. 오탐 신고는 규칙별로 집계해 점검 규칙 조정에 씁니다(규칙은 새 버전으로 바꾸며, 기존 결과는 바뀌지 않습니다). 자료실 권리·원본 삭제 신고는 즉시 비공개 처리됩니다.
- 로그에는 학생 원문을 남기지 않습니다. API 오류는 요청 ID와 마스킹된 메시지만 남기며, 키·토큰·전화번호 등은 `redactString`으로 가립니다.

## 7. live 전환 조건 (지금은 모두 미충족)

명세 6.3의 조건이 **모두** 참이어야 외부 호출이 실행됩니다. `/admin/providers`의 **live 전환 점검표**에서 엔드포인트별로 무엇이 빠져 있는지 확인할 수 있습니다. 실제 게이트 함수로 평가하며 외부 호출은 하지 않습니다. 현재 차단 상태와 근거는 README의 "live 차단 이유"에 있습니다. 전환 전에 필요한 것은 다음과 같습니다.

1. 공급자 다중 수강생 이용 허가 증빙을 `/admin/providers`에 기록(보관·표시·AI 가공 범위 포함).
2. 엔드포인트별 실제 단가·호출 한도 확인, 가격 버전 등록. 단가를 모르면 계속 차단됩니다.
3. live 예산 설정(기본 0), 최대 승인 금액.
4. RF08·RF10 파라미터와 미확인 문서(DCZW5V7A, 9UHXOXSF, tool/QPNFJRG1) 확인.
5. AI/OCR 제공자, 학생 데이터 전송 정책 결정.
6. 소량 실측(M5)으로 계약 fixture 확보. 그 전까지 live 어댑터는 "미검증"입니다.
7. 워커는 live 모드에서 `REDFOX_API_KEY`가 없으면 시작하지 않습니다. 실제 호출 경로가 연결된 것은 검색(RF01)과 음성 문안 추출(RF13/RF14)입니다. 다른 엔드포인트는 응답 형식을 확인하기 전까지 요청 전에 거부되고, 예약도 반환됩니다(ADR 0007, 0008).

## 8. 첫 실측(M5) 절차

승인된 범위 안에서만 진행합니다. 순서를 지켜 주세요.

1. **단가 등록**(운영자, 서버):
   ```bash
   pnpm price register --endpoint RF13 --unit call --unit-cost <단가> --currency CNY --evidence "<견적서/계약서 식별>" --verified-by <확인자 이메일>
   pnpm price register --endpoint RF14 --unit call --unit-cost <단가> --currency CNY --evidence "..." --verified-by <확인자 이메일>
   pnpm price list
   ```
2. **이용 허가**: `/admin/providers`에서 허가를 만들고(RF13·RF14, 수집·발췌 표시 등 계약 범위만 체크), 증빙 파일을 붙여 승인합니다.
3. **예산**: `/admin/usage`에서 이번 기간 조직 live 예산을 실측 상한으로 설정합니다. 학생별 예산도 따로 둘 수 있습니다.
4. **서버 설정**: 웹·워커 환경에 `APP_DATA_MODE=live`, `LIVE_PROVIDER_CALLS_ENABLED=true`, `TRANSCRIPT_ENABLED=true`를 넣고, 워커에는 `REDFOX_API_KEY`를 서버 secret으로 넣습니다. 그다음 `/admin/providers`에서 조직 live 스위치를 켭니다.
5. **점검표 확인**: `/admin/providers`의 live 전환 점검표에서 RF13·RF14가 "준비됨"인지 봅니다. 아니면 표시된 이유부터 해결합니다.
6. **1건 실행**: 학생 계정으로 영상 노트의 음성 문안 추출을 요청합니다. 견적의 실제 최대 비용을 확인하고 동의한 뒤 실행합니다.
7. **결과 확인**: `/admin/jobs`(작업 상태), `/admin/usage`(원장·예산)를 봅니다. `unknown_outcome`이 생기면 RedFox 측 사용 내역과 대조해 정산합니다.
8. **되돌리기**: 즉시 막으려면 kill 스위치를 켜거나 조직 live 스위치를 끕니다. 단가를 다시 막으려면 `pnpm price unverify --endpoint RF13`을 실행합니다.

## 9. 성능 기준 확인

`pnpm perf`를 실행하면 임시 DB에 합성 노트를 약 1만 건까지 복제한 뒤 주요 조회를 측정합니다. 측정 범위는 사용자 1명 반복과 동시 20명 혼합입니다. 명세 11장 파일럿 목표는 저장된 탐색 p95 2초, 일반 CRUD p95 1초입니다. 측정이 끝난 DB는 `pg_ctl -D .tmp/pg/data stop`으로 멈춥니다.


## Apify AP01 운영 준비와 복구

대상 Actor는 `zen-studio/rednote-note-detail-scraper`이며 선택한 노트 상세 1건을 조회합니다. RedFox 실패 시 자동 대체하지 않습니다.

- `/admin/providers`에서 공급자 Apify, 엔드포인트 AP01을 골라 허가를 등록합니다. 수집·메타데이터 표시·발췌 표시·미디어 표시·캐시 보관을 허용하고 양수 TTL을 지정합니다. 증빙을 연결한 뒤 승인합니다. AI 가공 허가는 이 기능에서 사용하지 않습니다.
- `/admin/usage`에서 별도의 USD 월 예산을 설정합니다. 기존 CNY 예산은 RedFox용으로 유지합니다.
- 실행당 모든 과금 항목과 Apify의 비용 제한 적용 조건을 확인한 후, 검증된 **USD/run 최대 금액**을 등록합니다. 시작 가격이나 points 잔액으로 추측하지 않습니다.

```bash
pnpm price list --provider apify
pnpm price register --provider apify --endpoint AP01 --unit run --currency USD \
  --unit-cost "$VERIFIED_MAX_USD_PER_RUN" --evidence "$PRICE_EVIDENCE" --verified-by "$OPERATOR_EMAIL"
pnpm price unverify --provider apify --endpoint AP01
```

위 변수는 운영자가 확인한 값으로 설정해야 하며 예시 실행 가격은 제공하지 않습니다. Actor 빌드를 바꾸면 입력·응답 계약과 가격을 다시 확인합니다. 토큰은 worker secret에만 등록합니다.

성공한 실행은 앱 원장에 예약 최대액으로 정산됩니다. 응답 유실, non-2xx, 형식 불일치 또는 저장 실패는 `unknown_outcome`으로 예약을 보존합니다. 자동 재실행하지 말고 Apify 콘솔의 해당 시간대 실행과 청구 내역을 확인하여 `/admin/usage`에서 증빙과 함께 정산합니다. 발송 표시만 있고 실제 실행이 없었던 경우도 확인 후 해제합니다. 앱은 원본 응답과 API 토큰을 기록하지 않습니다.

보완 자료는 허가 철회·만료 시 즉시 조회에서 제외되며 TTL 만료 후 워커가 매시간 삭제합니다. 표지 주소 자체의 만료는 별도로 검사합니다. Actor가 URL을 반환하더라도 브라우저에서 이미지가 보인다는 보장은 없으며 운영 확인이 남아 있습니다.


## 여러 페이지 수집·표지 일괄 보완 (ADR 0013)

탐색의 외부 조회에서 수집 목표를 50건 또는 100건으로 선택합니다. 최대 호출 수는 각각 5회/7회이며 RF02 호출 단가로 견적을 계산합니다. 성공하면 완료된 페이지 수만큼 정산하고 나머지 예약액을 해제합니다. 기간·주제 필터와 공급자 결과 부족 때문에 실제 표시 수가 목표보다 적을 수 있으며, 작업 상태에 확보 수와 종료 이유가 표시됩니다.

표지 없는 결과는 페이지 위의 Apify 일괄 보완 링크로 이동합니다. 선택된 최대 50개 노트 ID를 확인한 후 별도의 USD 총비용에 동의합니다. 요청당 실행 상한은 단일 노트 설정과 동일하며, 전체 예약액은 실행 상한×대상 수입니다. 전체 USD 예산이 부족하면 작업을 시작하지 않습니다. 한 번에 하나씩 진행하며 중단되면 완료 건수와 남은 작업을 확인할 수 있습니다.

중간 취소 또는 게이트 철회 시 이미 실행한 단계가 있다면 원장은 unknown_outcome을 유지합니다. 관리자 사용량 화면에서 공급자 청구 근거로 정산합니다. 현재 API 키 등록 사실은 사용자 진술이며 이 작업에서 Railway secret 값을 조회하지 않았습니다.
