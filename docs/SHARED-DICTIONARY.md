# 공용사전 운영 및 배포 체크리스트

## 현재 범위

기존 Supabase 초대 로그인과 조직 권한을 재사용합니다. 새 가입 시스템이나 공개 가입은 만들지 않습니다.

- 학생: `/app/dictionary`에서 해당 조직·데이터 모드의 공개 항목만 검색하고 선택합니다.
- 관리자: `/admin/dictionary`에서 JSON 등록 → 전체 변경 미리보기 → 검토 완료 → 별도 공개 반영을 진행합니다.
- 원자료: 관리자 전용 가져오기 테이블에만 보관합니다. 학생용 항목에는 뜻·분류·주의점 등 허용 필드만 복사합니다.
- 개인 AI 초안: 공용사전에 자동 추가하지 않습니다. 전송 내용과 결과 본문을 사용량 DB에 저장하지 않습니다.

기존 조사 루틴이 로컬 JSON을 갱신하는 것과 운영 사이트 반영은 별개입니다. 자동으로 운영 사전을 덮어쓰지 않습니다. 자료를 정리한 뒤 갱신된 JSON을 관리자 화면에서 가져오고 검토·승인해야 합니다.

## 가져오기 파일

기존 `xiaohongshu-dictionary.json` 형식을 사용합니다. 현재 파일은 태그 327개·표현 131개를 포함합니다. **이 파일이나 원자료 라이브러리를 공개 Git 저장소, 정적 웹 디렉터리, 클라이언트 번들에 넣지 마세요.**

- JSON 파일 2MB, 항목 최대 10,000개. 전체 multipart 요청도 별도로 제한합니다.
- 원자료 URL·인용·sourceIds 등은 학생용 DTO에서 제외합니다.
- `mainCategories`가 있으면 분류에 우선 사용합니다.
- 반복 가져오기는 동일 항목을 갱신하며, 입력 순서나 대소문자 변형 때문에 출처 분류·mock/live 표시를 바꾸지 않습니다.
- 검토 이후 다른 반영으로 사전이 바뀌면 오래된 검토본을 그대로 덮어쓰지 못하게 차단합니다. 최신 상태에서 다시 가져와 검토하세요.
- 인기·검색량·성과·효능은 이 사전으로 입증되지 않습니다. 관찰 횟수는 편집 자료 내 출현 횟수입니다.

## AI 작성 기능: 기본 꺼짐

활성화는 배포 및 비용 승인을 받은 뒤 별도로 합니다. 브라우저에 API 키를 넣지 않습니다.

필요한 서버 설정:

```dotenv
APP_DATA_MODE=live
AUTH_PROVIDER=supabase
LIVE_LLM_CALLS_ENABLED=true
DICTIONARY_AI_ENABLED=true
GEMINI_API_KEY=<서버 비밀 설정에만 입력>
```

기존 조직의 live/AI 스위치가 켜져 있고 kill 스위치가 꺼져 있어야 합니다. 키만 등록해도 실행되는 구조가 아닙니다. 데이터 수집 공급자의 설정은 변경하지 않습니다.

초기 제한은 코드와 DB에 고정되어 있습니다. **아직 운영 비용 승인을 뜻하지 않습니다.**

- 모델: `gemini-3.8-flash`.
- 학생별 하루 최대 3회, 한국 시간 기준. 여러 조직에 속해도 합산합니다.
- 배포 전체 월간 예약 상한 US$5, 한국 시간 기준.
- 시도마다 US$0.06을 보수적으로 예약하고 실패해도 예약액을 유지합니다. 따라서 월 최대 83회 시도가 가능합니다.
- 화면의 토큰 기반 예상액, DB 예약액, 실제 Google 청구액은 서로 다른 개념입니다. 정액 구독료가 아니며 운영 전 최신 공급자 단가와 청구 조건을 확인해야 합니다.
- 서명된 미리보기는 5분 유효합니다. 사용자·조직·내용에 묶이며 한 번만 실행됩니다.
- 예약 트랜잭션이 완료된 뒤 외부 요청을 한 번 보냅니다. 프로세스 중단이나 정산 실패가 이미 예약한 비용을 지우지 않습니다.
- 회원 탈퇴로 이미 예약한 비용 기록을 지워 월간 한도를 다시 열지 않습니다. 사용량에는 본문 없이 식별자·시간·모델·예약액·토큰 수만 남습니다. 운영 개인정보 안내와 이 메타데이터의 보관·삭제 정책을 별도로 확정하세요.
- 자동 재시도·백그라운드 생성·자동 게시가 없습니다.

## 배포 전

1. 기존 운영 브랜치의 최신 변경을 확인하고 충돌 없이 병합합니다.
2. 키, 원자료, node_modules, .next, 로컬 데이터베이스, 테스트 도구를 커밋하지 않습니다.
3. CI의 native PostgreSQL 통합 테스트와 기존 빌드/E2E를 통과시킵니다. 로컬 PGlite 검증은 native PostgreSQL 동시성·프로토콜 검증을 대체하지 않습니다.
4. `pnpm db:sql`로 초기 SQL 패키지를 재생성합니다. 운영에서는 기존 마이그레이션 실행기가 24·25만 추가 적용합니다. **seed/test shim을 운영에 적용하지 않습니다.**
5. DB 백업·롤백 방법, 개인정보 보관 정책, GitHub/Railway 반영 범위 및 AI 비용을 검토하고 최종 승인을 받습니다.
6. 기존 Railway web/worker와 Supabase를 재사용합니다. 신규 요금제나 별도 서버를 자동 생성하지 않습니다.
7. 배포 후 관리자 로그인 → 파일 가져오기 → 변경 검토 → 공개 반영을 별도 확인합니다. 테스트 계정이나 학생 초대를 자동 생성하지 않습니다.
8. 운영의 학생 권한, 다른 조직 격리, 원자료 비노출, AI 꺼짐/한도 및 health 응답을 확인합니다.

이 문서는 구현·검증·운영 절차입니다. 작성만으로 운영 배포, 데이터 이관, AI 예산 승인이 완료된 것은 아닙니다.
