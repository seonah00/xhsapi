# ADR 0013: 50/100건 목표 검색과 Apify 표지 일괄 보완

날짜: 2026-10-07 · 상태: 구현, 실제 호출·배포 전

## 사용자 요구와 구현

한두 건만 보이는 탐색을 개선하기 위해 외부 조회 목표를 기본 50건, 선택 100건으로 변경합니다. 저장 자료 화면도 페이지당 50건을 표시합니다. 실제 결과가 부족할 때 임의 자료를 만들어 목표를 채우지 않습니다.

RedFox RF02의 [공식 문서](https://redfox.hk/apis/xiaohongshu/384C6W6B)는 offset을 0부터 페이지마다 20씩 증가하도록 설명합니다(2026-10-07 확인). 이 계약을 사용하며 RF01 키워드 검색의 미확인 페이지 파라미터는 추측하지 않습니다. 50/100건 목표 기능은 RF02 허가와 검증된 호출/page 단가가 없으면 차단합니다. 기존 1회 검색 서비스 계약은 유지합니다.

- 50건 목표: 최대 5페이지, 100건 목표: 최대 7페이지. 중복·기간 필터로 줄어드는 경우를 위해 목표에 필요한 페이지 수에 2페이지를 더한 상한입니다.
- 고유 노트 기준으로 목표에 도달하면 종료합니다. 마지막 페이지 전체를 저장하므로 50건 목표에서 60건을 확보할 수 있습니다.
- hasMore=false, 빈 원본 페이지, 같은 페이지 반복, 승인한 페이지 상한 도달 시 종료합니다. 기간 필터 때문에 0건이 된 페이지는 원본 페이지가 비어 있지 않으면 다음 페이지를 진행합니다.
- 성공 시 실제 완료한 페이지 수의 비용만 정산하고 사용하지 않은 페이지의 예약은 해제합니다. 실패한 요청의 과금이 불확실하면 예약을 unknown_outcome으로 유지합니다.
- 화면에는 확보 건수, 목표, 조회 페이지 수, 종료 이유를 표시합니다. 주제·형식·검색어 필터에 따라 저장된 수보다 표시되는 수가 적을 수 있습니다.

## Apify 표지 보완

현재 페이지에서 표지 주소가 없거나 만료된 노트를 최대 50건씩 모아 **표지 없는 N건 Apify 보완**으로 이동합니다. 대상 목록, 실행 횟수, USD 총비용을 확인·동의한 뒤 실행합니다. RedFox 조회와 통화가 다르므로 견적과 동의를 분리합니다. 추가 유료 작업이 검색 성공이나 이미지 로딩 실패만으로 시작되지는 않습니다.

견적은 대상 ID 배열과 Actor 빌드, 실행당 상한을 고정합니다. 예산은 `대상 수 × 검증된 USD/run 상한`을 예약하며 각 Actor 요청에는 실행당 상한만 전송합니다. 이미 있던 단일 노트 보완 화면도 유지합니다. 실제 반환된 URL이 표시 가능한지는 운영 검증이 필요합니다.

## 작업 지속성과 비용

검색은 한 페이지, Apify는 한 노트씩 작업 임대 안에서 실행합니다. 발송 전에 표시를 영속화하고, 응답 저장과 다음 진행 위치를 같은 DB 트랜잭션에 기록합니다. 발송 표시가 남은 작업은 재전송하지 않고 unknown_outcome 처리합니다. 완료 기록만 남고 최종 정산 전 중단되면 다음 실행은 정산만 수행합니다.

각 단계마다 회원·조직 스위치·허가·동의를 다시 확인합니다. 대상과 목표 수는 승인된 견적 범위와 비교합니다. 단계 사이 취소는 전송 이력이 없으면 해제, 이미 처리한 단계가 있으면 과금 확인이 필요하므로 unknown_outcome을 유지합니다. 관리자 정산 절차는 OPERATIONS를 따릅니다.

## 검증 범위

- 단위 테스트: 페이지 이동, 잘못된 offset, 중복·빈 페이지·기간 필터·상한, 1~50개 고유 보완 대상, 작업 재개·응답 유실·중간 중지.
- 별도 PGlite SQL smoke: 실제 마이그레이션과 SQL/RLS로 60건 수집·50+10건 조회, 단가별 예약/정산, Apify 2건 보완, 조직 격리·허가 철회, 취소·동의 철회·예산 초과·범위 변조 검증. 실제 수집 API는 가짜 fetch로 대체합니다.
- PGlite는 단일 프로세스 테스트이므로 native PostgreSQL 동시성·전체 DB 통합 테스트와 브라우저 E2E를 대체하지 않습니다. 현 환경의 공유 메모리 제한으로 이 검증은 별도 환경에서 마쳐야 합니다.
