# ADR 0009 — 실제 로그인(Supabase Auth)·비공개 저장소·Railway 배포 준비

날짜: 2026-10-06 · 상태: 채택 (로컬 가짜 서버로 자동 검증, 2026-10-06 실제 Supabase·Railway 첫 배포에서 운영자 확인)

## 결정

1. **로그인 방식**: 서버가 Supabase Auth에 이메일·비밀번호를 확인하고, 그다음 기존과 같은 **서명된 자체 세션 쿠키**를 발급한다. Supabase 토큰은 저장하지 않는다. DB 접근은 지금처럼 서버가 `authenticated` 역할과 `auth.uid()` claim으로 RLS 아래에서 실행한다. 브라우저에는 Supabase 키가 가지 않는다.
2. **가입**: 공개 가입은 없다. 초대 링크로만 계정을 만든다. 순서는 초대 유효성 확인 → 관리자 API로 계정 생성(이메일 확인 처리) → 즉시 초대 사용이다. 초대에 이메일이 지정돼 있으면 그 이메일만 가입할 수 있다. 1회용 초대 링크 자체가 본인 확인 수단이다.
3. **메일 없이 비밀번호 설정**: 메일 발송은 별도 승인 항목이므로, Supabase의 복구 토큰(hashed_token)으로 **우리 도메인의 1회용 링크**(`/auth/set-password?token=`)를 만들어 관리자·운영자가 직접 전달한다. 토큰은 화면을 열 때가 아니라 제출할 때만 소모한다(링크 미리보기 봇 대응).
4. **조직 간 탈취 방지**: 조직 관리자는 **다른 조직에 활성 멤버십이 없는 사용자**에게만, 그리고 본인이 아닌 경우에만 링크를 만들 수 있다. 발급은 감사 기록에 남긴다(링크 자체는 저장하지 않음).
5. **비밀번호 기준**: 10자 이상, 72바이트 이하(bcrypt 한계), 이메일 아이디 포함 금지. 로그인 실패 문구는 하나로 통일했다. 계정별 시도 제한은 프로세스 메모리에서 한다(Supabase 자체 제한과 별개).
6. **환경 규칙**: live 모드는 `AUTH_PROVIDER=supabase`가 필수다(데모 로그인은 mock 전용). Supabase 주소와 `APP_BASE_URL`은 https만 허용하고, 테스트용 localhost만 예외다. 링크 주소는 요청의 Host 헤더가 아니라 `APP_BASE_URL`로 만든다(헤더 주입 방지).
7. **저장소**: `ObjectStorage` 인터페이스에 Supabase 비공개 버킷 구현을 추가했다. 서비스 키로만 접근하고, 덮어쓰기는 하지 않는다(`x-upsert: false`). 브라우저에는 기존 게이트웨이로만 전달한다.
8. **외부 연결 차단**: 웹은 DB와 Supabase 주소만, 워커는 여기에 live일 때 `redfox.hk`만 추가로 허용한다.
9. **운영 데이터**: 기본 분류는 데모 시드에서 마이그레이션(0013)으로 옮겼다. 데모 계정·조직은 `seed.sql`에만 있고 운영에는 적용하지 않는다. 첫 조직·관리자는 `pnpm bootstrap:org`로 만든다.
10. **배포 형태**: Railway에 웹·워커를 각각 서비스로 둔다(Dockerfile 2개, non-root 실행, 헬스체크). Vercel은 상시 워커를 못 띄워 제외했다. HTTPS 주소로 빌드하면 HSTS를 붙인다.
11. **배포 직후 점검**: 실제 Supabase에서 이 앱의 전제가 성립하는지 확인하는 `pnpm verify:db`를 둔다. 확인 항목은 역할 전환, `auth.uid()`, RLS, 마이그레이션·기본 데이터, 데모 계정 부재다.

## 검증과 한계

- 로컬 가짜 Supabase 서버(`tests/support/fake-supabase.ts`)로 DB 통합 테스트 8개와 E2E 1개를 돌렸다. E2E는 부트스트랩 → 비밀번호 설정 → 로그인 → 초대 가입 → 비공개 업로드 → 재설정 링크 흐름을 확인한다. 가짜 서버는 공개 API 형태를 본뜬 것이라 실제 Supabase와의 차이는 배포 후 점검으로 확인해야 한다.
- Docker 이미지 빌드는 이 개발 환경에서 이미지 저장소 접속이 막혀(정책 403) 수행하지 못했다. 이미지 안의 단계(잠금 파일 그대로 설치, 비밀값 없이 빌드)는 로컬에서 통과했고, 첫 배포에서 Railway 빌더가 `Dockerfile.worker`로 이미지를 빌드했다. `deploy/supabase/verify.sql`은 실제 Supabase에서 모든 줄 `ok`였다.
- Railway 설정 파일 형식과 Supabase Session pooler·TLS 설정은 공식 문서 기준으로 작성했다. 2026-10-06 첫 실제 배포(Railway web·worker + Supabase)에서 운영자가 확인: 마이그레이션 13개 적용, `/api/health` 응답, 첫 관리자 생성(1회용 링크) → 비밀번호 설정 → 로그인, 학생 초대 가입, 이미지 업로드가 비공개 버킷 `private-assets`에 저장되고 화면에 표시됨, 워커 mock 모드 시작·만료 정리 실행.
- 첫 배포에서 드러나 고친 것: worker 서비스가 이미지의 시작 인자(`web`) 때문에 웹으로 뜨던 문제(`XHS_SERVICE`가 우선), 관리자가 로그인한 브라우저에서 초대 링크를 열면 가입 폼이 보이지 않던 문제.
